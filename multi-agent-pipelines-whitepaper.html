Engineering Robust
Multi-Agent Coding Pipelines

A Control-Plane Reference Architecture for Intent Integrity, Evaluation Integrity, and Contained Execution in Autonomous Software Teams.

Reference Architecture & Control Spec Evidence Taxonomy: Empirical Research, Docs & Preprints Focus: Planning/Execution Split, Evaluation Surface Immutability & Egress Isolation
Executive Abstract

Autonomous software agents can produce changes that appear credible, pass incomplete test suites, and still violate intended behavior, security constraints, or integration assumptions. These risks compound when multiple agents plan, implement, test, and merge changes across shared or partially isolated state. Prompt instructions, personas, and dynamically retrieved rulebooks remain useful for task guidance, but they are not authoritative enforcement mechanisms; their effect depends on probabilistic model behavior and context selection. A robust agentic software engineering pipeline therefore separates guidance from enforcement: agents propose and implement changes, while an external control plane constrains what they can modify, what they can access, how they are evaluated, and what evidence is required prior to merge. This paper presents a vendor-neutral reference architecture built around three distinct planes: a planning plane that produces versioned contracts and independently owned evaluation artifacts; an execution plane that operates in isolated, least-privilege environments; and a control plane that coordinates state, verifies artifacts, records evidence, and governs merge decisions. The architecture bounds—rather than eliminates—semantic divergence, evaluation gaming, coordination conflicts, and unauthorized external effects.

1. Scope, Definitions, and Assurance Levels

Before examining failure modes and mechanical controls, we establish operational boundaries, define terminology, and outline a graduated maturity model for pipeline assurance.

1.1 Definition of Mechanical Controls

In an agentic assurance context, we define a mechanical control as:

Mechanical Control Definition

An externally enforced, machine-evaluable constraint whose enforcement and verification are independent of the executing agent's natural-language compliance claim or probabilistic token generation. Examples include operating-system read-only volume mounts, signed artifact digest verification, capability-restricted tool invocation schemas, policy-enforced egress proxies, compiler type checks, AST lint rules, and branch protection merge barriers.

Mechanical controls are not assumed to be infallible or capable of discovering unstated intent; rather, their execution is independent of the agent under evaluation.

1.2 Operational Scope

This architecture addresses repository-level autonomous software modification wherein one or more LLM agents ingest source code, formulate technical plans, modify designated implementation files, execute approved tools, and submit candidate patches. The architecture operates under explicit boundary conditions:

  • In Scope: Guardrails against semantic intent drift, test modification / evaluation gaming, stale-state workspace clobbering, secret extraction into guest environments, unauthorized network egress, and unreviewed production merges.
  • Out of Scope: Formal verification of arbitrary algorithmic correctness, real-time protection against fully privileged bare-metal host compromise, or automated discovery of unstated human business requirements.

1.3 Actor and Trust Zone Model

To eliminate ambiguity between agent capability and system authority, the architecture defines six operational entities across distinct trust boundaries:

Actor / Component Trust Level Permitted Actions Prohibited Actions
Human Approver Trusted Approve frozen contract schemas, authorize production branch merges, grant policy exception waivers. Bypass CI evidence requirements without an auditable, recorded waiver manifest.
Planning Agent Semi-Trusted Generate technical specifications, author typed schemas, propose frozen TDD suites, assign risk labels. Directly write to production branches, mutate CI workflows, or execute implementation code.
Execution Agent Untrusted for Enforcement Read approved contracts, edit allowlisted implementation files within an isolated guest workspace, invoke policy-checked tools. Modify test files, alter lockfiles, change CI definitions, access raw credentials, or contact unauthorized networks.
Control Plane Trusted Computing Base Provision isolated runners/worktrees, enforce write allowlists, mediate egress via host proxy, retain run evidence, govern merge gates. Generate unreviewed production code changes or bypass configured gating policies.
CI Evaluator Trusted Computing Base Execute pinned test suites against candidate patches, run mutation tests, emit cryptographically bound attestations. Consume unpinned, executor-modifiable test configurations or unverified dependency sources.
External Services Conditionally Trusted Serve allowlisted package dependencies and verified API responses over proxy-mediated channels. Receive unredacted repository state, unmasked credentials, or unconstrained outbound network requests.
Table 1. Actor and trust boundary definitions across the agentic lifecycle.

1.4 Agentic Assurance Maturity Levels

Organizations adopt mechanical controls progressively. We define six assurance levels to structure deployment milestones:

Level Description Minimum Required Mechanical Controls
L0 Prompt-Managed System prompts, conversational conventions, manual copy-paste code reviews. No mechanical boundaries.
L1 Workspace-Isolated Separate Git worktrees or independent containers per agent run; protected main branch with pull request requirements.
L2 Evaluation-Protected Execution agents cannot alter evaluation surfaces; read-only test mounts, immutable CI workflows, writable file path allowlists.
L3 Capability-Contained Default-deny network egress, host-side credential mediation proxy, execution in dedicated microVM or sandbox runner, tool policy allowlists.
L4 Evidence-Attested Hermetic build images, pinned dependency lockfile digests, signed task manifests, structured tool-call audit logs, reproducible CI attestations.
L5 High-Assurance Independent dual-agent test authorship, automated mutation testing score thresholds, dependency-aware conflict detection, dual human sign-off.

2. Why Prompt Guidance Is Not Enforcement

Natural-language instructions improve agent behavior, but they cannot establish an independently enforceable boundary. When an agent receives an instruction in its prompt, that same agent is responsible for interpreting the rule, evaluating edge cases, and asserting whether it complied. In safety- or integrity-sensitive software engineering pipelines, this conflates guidance with enforcement.

2.1 Statistical and Contextual Limits of Prompts

Empirical research identifies fundamental constraints in prompt-only governance:

  • Context Degradation and Retrieval Attenuation: As conversational context expands, retrieval fidelity drops significantly in the middle of the context window (Lost in the Middle, Liu et al., 2024). Placing architectural rules or security constraints in prompt headers or memory files does not guarantee attention during long multi-turn tool-call sequences.
  • Inconsistent Instruction Hierarchies: Multi-agent systems frequently rely on system/user prompt separation to enforce privileged constraints. However, empirical evaluations demonstrate that models do not reliably prioritize privileged system instructions over user inputs or tool outputs when formatting conflicts or counter-framing occur (Control Illusion, Geng et al., AAAI 2026).
  • Context Pollution Overhead: Accumulating past post-mortems and negative instructions in dynamic memory files (e.g., MEMORIES.md) inflates token costs and increases latency. Unconstrained broadcast communication topologies have been shown to elevate hallucination rates across collaborating agents (Zhang et al., 2026), whereas structured state machines (SEMAP, Mao et al., 2025) bound context to immediate task parameters.

2.2 The Three Orthogonal Pipeline Properties

To avoid conflating mechanisms, the architecture strictly distinguishes three orthogonal properties:

  • Safety & Security (Containment): Preventing unauthorized data exfiltration, credential leakage, arbitrary network access, or lateral host movement (enforced via microVM sandboxes, host credential proxies, and egress filters).
  • Integrity & Correctness (Verification): Ensuring proposed changes conform to interface contracts, satisfy independent specifications, resist mutation, and pass deterministic type/build gates (enforced via schemas, compilers, and immutable test suites).
  • Coordination Consistency (State Management): Preventing concurrent workspace overwrites, stale interface assumptions, and unmanaged merge conflicts (enforced via isolated worktrees, dependency-aware write checks, and merge locks).
Governance Layer Primary Purpose Typical Primitives Assurance Property
Agent Guidance Improve quality, efficiency, and stylistic alignment of candidate changes. Personas, domain skills, reference examples, coding conventions, retrieved API documentation. Probabilistic and advisory (non-binding).
Mechanical Control Plane Enforce non-negotiable security, integrity, and release boundaries. Read-only evaluation mounts, schema validators, egress proxies, capability policies, merge gates. Externally enforced and machine-auditable.
Table 3. Dual-layer governance model: Guidance vs. Mechanical Control Plane.

3. Documented Empirical Failure Modes

Engineering a robust control plane requires cataloging the specific failure modes observed in autonomous coding pipelines and mapping each to an empirical evidence base.

  • Intent Divergence & Semantic Drift: When planning agents communicate specifications in natural language, implementing agents frequently adopt diverging interface assumptions (Semantic Consensus, Acharya, 2026; CodeCtx, Baker, 2026). Natural language agreements lack machine-checkable boundary definitions.
  • Evaluation Gaming and Test-Oracle Uncertainty: Automated test execution (exit 0) is bounded evidence, not absolute proof of correctness. Empirical audits reveal dual-directional oracle failures:
    • False Acceptance (Weak Oracles): In an empirical audit of SWE-bench Verified, Rajan (2026) found that 28.5% of evaluated tasks accepted Docker-verified patches that were functionally defective due to incomplete assertion coverage.
    • False Rejection & Ambiguity: Conversely, in an audit of 138 difficult failures, OpenAI (2026) reported that 59.4% of failed instances suffered from flawed reference tests or underspecified descriptions that rejected correct implementations.
  • Same-Agent TDD Pathologies: When an executing agent generates both test fixtures and implementation code, it often produces tautological assertions that pass unconditionally (Autonoma, 2025). In an empirical evaluation, Böckeler (2024) documented that single-agent TDD loops yielded negligible mutation testing improvements because agents skipped initial failing states or tailored assertions to match existing code bugs.
  • Stale-State Coordination Failures: While Git worktrees provide separate working directories, they do not prevent agents from committing changes based on obsolete interface assumptions. As demonstrated by STORM (Liu et al., 2026), multi-agent collaboration requires state-aware mediation that tracks dependency reads and blocks stale writes against shared abstractions. In production systems, uncoordinated reads against short-lived caches can trigger cascade failures across otherwise well-prompted agents (Bhaumik, 2024).
  • Boundary Escape & Credential Disclosure: Coding agents granted unconstrained shell access can leak environment variables, query cloud metadata endpoints (e.g., 169.254.169.254), or invoke billable third-party APIs during test execution instead of using local mocks.

Specification 2: Immutable Evaluation Surface

The evaluation surface comprises all files and configurations that determine whether candidate code is accepted. The control plane binds this surface as an immutable bundle:

  • Test Suites & Fixtures: All unit, integration, and end-to-end test files generated during the planning phase.
  • Dependency Resolution: Lockfiles (e.g., package-lock.json, poetry.lock) and package configuration manifests.
  • Build & CI Scripts: Pipeline definitions (e.g., .github/workflows/), linter configs, compiler flags, and test runner arguments.
  • Evaluation Runner Image: Pinned OCI digest of the container running the evaluation suite.

Specification 3: Sandbox Egress & Credential Containment Policy

Execution environments operate with default-deny network access. Necessary external communication (e.g., package registry downloads) is routed through a host-side proxy that strips guest credentials and verifies target hosts against an allowlist:

CONTAINMENT_POLICY.YAML HOST-SIDE ENFORCEMENT 
version: "1.0"
metadata:
  policy_id: "pol-sbx-strict-v2"
  enforcement_tier: "L3_CAPABILITY_CONTAINED"

  writable_paths:
    - "src/modules/billing/**"
    - "src/utils/math/**"
  read_only_mounts:
    - host_path: "/var/bundles/eval-task-4819"
      guest_path: "/workspace/tests"
  denied_paths:
    - ".git/**"
    - ".github/**"
    - "package.json"
    - "package-lock.json"
network:
  default_egress: "deny"
  allowlist:
    - host: "registry.npmjs.org"
      port: 443
      protocol: "https"
    - host: "pypi.org"
      port: 443
      protocol: "https"
credential_mediation:
  mode: "host_proxy"

      injected_on_host: true
      guest_visible: false

5. Operational Pipeline and Assurance State Machine

The reference architecture translates governance rules into an automated, multi-stage state machine with formal transition criteria and failure handling.

Stage Immutable Inputs Mutable Outputs Verification Gate Failure Disposition
1. Contract Approval Requirements, Architecture Decision Records (ADRs). Versioned OpenAPI / JSON schemas, typed interfaces, task manifest. Schema validation; explicit human approver signature. Reject to Planning; refine requirements.
2. Evaluation Bundle Creation Approved contract, base repository commit. Independent test suites, fixtures, runner manifest. Baseline runner verifies tests fail cleanly on empty stubs (red state). Reject to QA / Planning; rewrite invalid fixtures.
3. Execution Admission Frozen contract, evaluation bundle, task manifest. Isolated Git worktree, sandboxed microVM container. Policy engine validates file allowlist, path deny-rules, and egress rules. Halt sandbox startup; alert platform operator.
4. Implementation Execution Task manifest, allowlisted source files, read-only tests. Candidate patch diffs, local execution logs. Local retry budget (max 3), local compiler/linter AST checks. Quarantine branch; capture diagnostic evidence bundle.
5. CI Evaluation & Attestation Candidate patch, frozen evaluation bundle. CI build logs, mutation test scores, attestation record. Pinned test pass (exit 0), mutation threshold satisfied, conflict guard pass. Quarantine branch; return structured failure log to Planning.
6. Production Merge Decision Signed evidence bundle, cryptographic CI attestation. Production branch merge commit or explicit rejection. Human review, CODEOWNERS policy check, risk matrix evaluation. Reject PR or grant time-bound waiver with recorded justification.
Table 5. Multi-agent lifecycle state machine: inputs, outputs, gates, and dispositions.

5.1 The Four Mechanical Assurance Rules

The state machine enforces four core operational rules:

  1. 1. Treat Automated Success as Bounded Evidence A successful build, type check, or test pass (exit 0) confirms conformance only to the specific assertions executed. It does not establish full behavioral correctness. Pipeline gates must require defense-in-depth verification (static analysis, schema conformance, mutation testing, and review) rather than relying on binary test results as a comprehensive oracle.
  2. 2. Preserve Total Evaluator Independence An execution agent must have zero capability to alter the evaluation suite, test fixtures, test runner commands, dependency lockfiles, compiler options, or CI workflows. The entire evaluation surface must be bound to the task manifest and mounted as read-only volumes.
  3. 3. Enforce Layered Adequacy Checks In safety-critical or core architectural modules, the CI evaluator must inject automated mutation testing (e.g., Mutmut, Stryker) to verify that the test suite detects intentional semantic mutations. For general codebases, mutation testing is applied on a calibrated risk-tier basis during PR evaluation or nightly regression runs.
  4. 4. Enforce Bounded Autonomy with Evidence-Preserving Quarantine When an agent exceeds its retry budget, triggers a policy violation, or fails evaluation gates, the control plane immediately revokes execution capabilities and quarantines the branch. Crucially, the system does not discard execution artifacts; it archives the task manifest, tool-call audit logs, patch diffs, test output, and container digests for post-mortem analysis and policy refinement.

6.1 Residual Risk and Defense-in-Depth Mitigations

A rigorous reference architecture must explicitly identify residual risks that fall outside automated control-plane guarantees:

Residual Risk Failure Mode Description Recommended Defense-in-Depth Mitigation
Unstated Business Intent The code satisfies all formal schemas and unit tests but implements a commercially incorrect workflow. Mandatory human domain-expert review during contract approval; staged feature-flag rollouts.
Upstream Dependency Poisoning An allowlisted package repository serves a compromised sub-dependency that passes build gates. Software Bill of Materials (SBOM) scanning, dependency pinning, and vulnerability database auditing.
Proxied Capability Misuse An agent issues excessive or abusive API requests through an authorized host proxy. Granular rate limiting, path/method allowlisting, and anomaly detection on host proxy traffic.
Host / Hypervisor Escape A zero-day exploit in container or virtualization software breaches host isolation. Kernel hardening (e.g., seccomp, AppArmor), ephemeral VM destruction, least-privilege host daemons.
Timing & Concurrency Flaws Candidate patches pass single-threaded CI runs but deadlock under production load. Automated load/stress testing in staging environments; telemetry canary monitoring prior to 100% traffic shift.
