// EXECUTIVE_SUMMARY

Buying new security tools does not mean your network is safe. In defense projects, teams must finish all 152 tasks required by the DoD Zero Trust Roadmap and prove it on a real project schedule. Security scanners and log tools give you lots of data, but they do not assemble audit proof or track project tasks. The Splunk App for Zero Trust Compliance (Splunkbase #9582) runs right inside Splunk Enterprise 10.4+. It replaces messy Excel sheets with a simple 5-column planning board, automatic project tracking, a built-in schedule calculator (| getcriticalpath), and a locked vault for proof files.

1. The Problem: Buying a Tool Does Not Finish the Job

Setting up Zero Trust in defense programs usually gets stuck because teams think buying new tools solves the problem. Leaders buy lots of separate software (such as login portals, microsegmentation tools, and virus checkers). But when inspectors arrive for an audit, they find that many basic tasks were never actually done or proven.

The DoD Zero Trust Roadmap and NIST SP 800-207 demand clear results across seven core areas (pillars):

1. User (Who is logging in)
2. Device (What phone or laptop is connecting)
3. Applications & Workloads (What programs are running)
4. Data (What files are being opened)
5. Network & Environment (What network paths are open)
6. Automation & Orchestration (How computers run tasks without humans)
7. Visibility & Analytics (Seeing and understanding the logs)

Each of the 152 activities has strict rules: who must do it first, when it must finish, and what proof is needed. A log viewer gives you raw lines of text; it does not give the Authorizing Official (AO) the signed proof required to approve your system.

3. How Work Gets Done: The 5-Step Delivery Board

To stop projects from falling behind schedule, the app uses a simple 5-step board:

Backlog → To Do → In Progress → Testing / In Review → Done / Accepted (Verified by Security Officer)

Clear roles ensure that work is checked properly:

  • Technical Worker: Picks tasks for the sprint, opens the proof drawer, attaches the digital fingerprint of the log files, and moves the card to Testing / In Review. Workers cannot mark their own cards as Done.
  • Project Manager: Makes sure the team does not take on too many tasks at once and keeps the project on schedule.
  • Security Officer (ISSO / ISSM): Checks the test results. A task can only be marked as Done if the program has a verified log record showing the security check passed. Without that proof, the system blocks the card.

4. Critical Path Engine & Integrated Master Schedule

Compliance tracking without an operational schedule results in unmanaged blockers. The application introduces a custom Splunk search command, | getcriticalpath (implemented in bin/get_critical_path.py), which executes a server-side Directed Acyclic Graph (DAG) Critical Path Method (CPM) using Kahn's topological sort.

The engine computes early and late start/finish dates alongside total float/slack for all milestone dependencies. The calendar logic dynamically calculates true operational time by skipping:

  • Weekend calendar intervals (Saturday/Sunday).
  • All 11 US statutory federal/DoD public holidays, including weekend observance shifts (e.g. Friday observance for Saturday holidays, Monday observance for Sunday holidays).
  • Project-wide team PTO exclusions defined in the pto_tok macro.

The resulting Gantt interface (zt_ims_gantt) provides real-time Schedule Performance Index (SPI) metrics and highlights critical-path milestone chains that risk slipping program Authority to Operate (ATO) deadlines.

5. Proof of Delivery (PoD) Vault & REST Endpoints

// MATURITY_NOTICE: EARLY-STAGE PILOT & PROOF OF CONCEPT (PoC)

The Kanban planning pipeline and the prototype AI review agent (which inspects recorded index telemetry to draft Proof of Delivery records) are early-stage Proofs of Concept (PoCs). Released openly on Splunkbase (#9582) under open-source licensing, these modules are designed for defense community co-creation and operational feedback.

Compliance is proven by cryptographically bound evidence, not spreadsheet checkboxes. To satisfy a Zero Trust Operational Milestone (ZTOM) across the 152 activities of the DoD Zero Trust Execution Roadmap (COAs 1 to 3), each card in the planning pipeline opens a structured slide-out Proof of Delivery (PoD) drawer governed by zt_pod_handler.py. The drawer is organized into three distinct verification sections:

Fig 5.1: The Three-Part Proof of Delivery (PoD) Architecture for Satisfying DoD Zero Trust Milestones.
  • Section 2 (COA Baseline & Federal Registries): Establishes the authoritative DoD requirement, target maturity tier, and DAG predecessor constraints. For perimeter and software controls, this section links directly to statutory mandates including PPSM (DoDI 8551.01) Central Registry categories, CAL (Connection Approval List) authorization dates, and CSAL (Cybersecurity Software Authorization List) software baselines.
  • Section 3 (Work in Progress & Operational Gaps): Documents active engineering tasks, uncovered attack surfaces, and AI-assisted gap analysis. Explicitly flags unapproved ports, un-peered Cloud Access Point (CAP) subnets, and un-allowlisted binaries.
  • Section 4 (Record & Triage Evidence Vault): Contains the cryptographic SHA-256 evidence digests and Splunk CIM query proofs (such as Network_Traffic port validation and Endpoint.Processes binary hash matching) required for formal ISSO sign-off. Unresolved gaps and non-compliant flows automatically trigger POA&M milestones formatted for TA-suhlabs-eMASS (#8253).

6. Architecture Topology: AWS-DFD-Visualizer (Splunkbase #8628)

To bridge the gap between compliance schedules and live cloud infrastructure, companion project AWS-DFD-Visualizer (Splunkbase #8628, v2.8.7) renders cloud asset inventory onto NIST SP 800-207 Three-Plane swimlanes:

POLICY COMPONENTS IDENTIFIED IN TOPOLOGY

  • PEP (Policy Enforcement Point) & PIP (Policy Information Point): Workload sensors and posture checkers fed by ForeScout C2C, Trellix, Microsoft Defender for Endpoint (MDE), and Tenable.
  • PDP (Policy Decision Point), PE (Policy Engine), & PA (Policy Administrator): Orchestrated control logic anchored by enterprise SIEM policies and automated playbooks.
  • Perimeter & Host Boundaries (CAL, CSAL, PPSM): Topologies map Cloud Access Points (CAP) and peering gateways against active Connection Approval List (CAL) packages, cross-reference boundary firewall ACLs against DISA Ports, Protocols, and Services Management (PPSM under DoDI 8551.01) categories, and track host binary execution against Cybersecurity Software Authorization Lists (CSAL).
// CLAIMS_BOUNDARY: OBSERVATION VS. ENFORCEMENT

AWS-DFD-Visualizer detects CSP asset environments (AWS, Azure, GCP) and marks topology paths that miss an expected control, such as unapproved direct SSH (port 22) ingress. A marked path is an operational finding to review. It does not prove that a policy engine actively dropped or blocked unauthorized traffic, nor does diagram generation constitute an automated compliance certificate. A formal audit determination remains an independent regulatory review of cryptographic evidence.

7. System Boundaries & Operational Reality

In accordance with SuhLabs engineering principles, the capabilities and boundaries of the v1.1.7 pilot release are documented transparently:

Table 7.1: Documented system boundaries and technical limits in v1.1.7
Subsystem Implementation Reality in v1.1.7 Documented Boundary & Next Stage
Cross-Collection Sync Best-effort update-only sync from zt_agile_stories to compliance and IMS collections. Sync updates existing records. It is not a distributed two-phase atomic commit (2PC). If an update fails, an error is recorded to _internal.
ISSO / EDIPI Stage-Gate Workflow gating uses simulated DoD EDIPI digital signatures to enforce verification criteria. The server binds the SHA-256 of the acceptance. Hardware smartcard CAC mutual TLS authentication is queued for the post-pilot ATO milestone.
Predictive Risk Analytics Risk scoring and maturity tier evaluation run on native Splunk SPL eval over KV lookups. No external MLTK (Machine Learning Toolkit) app dependency is required. Scoring is deterministic rule logic, not black-box neural inference.
CPM Predecessors Server-side topological sort in | getcriticalpath operates on comma-separated milestone IDs. Predecessors formatted as semicolon-separated roadmap titles are ignored by CPM calculations until mapped to milestone IDs.
Discovery Telemetry Automated discovery scheduled searches populate observation state in the KV store. Telemetry volume does not automatically mark an activity Compliant. A single passing hash confirms outcome proof; continuous authorization (cATO) requires recurring verification.
CAL / CSAL / PPSM & eMASS Sync Telemetry correlation against KV Store lookups (zt_ppsm_registry, zt_csal_manifest). Unapproved flows generate POA&M milestones via TA-suhlabs-eMASS (#8253). Splunk detects and documents violations for AO review; Splunk does not inline drop packets at the wire without an external PDP/PEP firewall integration.
