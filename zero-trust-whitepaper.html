// EXECUTIVE_SUMMARY

Zero Trust initiatives stall when treated as procurement exercises. Defense programs must satisfy all 152 activities mandated by the DoD Zero Trust Execution Roadmap (COAs 1–3) with full audit traceability to an Integrated Master Schedule (IMS). Commercial SIEM, EDR, and C2C tools generate telemetry, but they do not assemble cryptographic proof or manage project delivery. The Splunk App for Zero Trust Compliance (v1.1.7, Splunkbase #9582) runs natively inside Splunk Enterprise 10.4+, replacing CSV spreadsheets with a 5-column Kanban planning board, automated KV Store state projections, a DAG critical path method (CPM) search command (| getcriticalpath), and a cryptographic Proof of Delivery (PoD) vault.

1. The Operator Constraint: Buying a Tool Does Not Close a Task

Implementing Zero Trust (ZT) across defense programs frequently breaks down because organizations mistake vendor procurement for operational delivery. When functional owners treat roadmap activities as commercial software purchases, they deploy disparate tools—identity providers, microsegmentation agents, endpoint sensors—and discover at audit time that requirements remain unsatisfied.

The DoD Zero Trust Execution Roadmap and NIST SP 800-207 define explicit operational outcomes across seven architectural pillars:

1. User (Identity)
2. Device
3. Applications & Workloads
4. Data
5. Network & Environment
6. Automation & Orchestration
7. Visibility & Analytics

Each of the 152 activities specifies target maturity tiers, execution phases, and prerequisite predecessor dependencies. Satisfying an activity outcome requires evaluating which control is in place, what telemetry it observes, and which cryptographic evidence proves delivery. A SIEM or an EDR provides raw logs; it does not produce the defensible record required for an Authorizing Official (AO) or ISSO sign-off.

3. The Agile × Zero Trust Operational Delivery Loop

To prevent multi-year waterfall compliance debt, the application maps agile sprint mechanisms directly to DoD Zero Trust Operational Milestones (ZTOM). Work progresses through a 5-column Kanban pipeline:

Backlog → To Do → In Progress → Testing / In Review → Done / Certified

Role-governed stage gates ensure regulatory integrity throughout the loop:

  • Technical SME: Pulls committed activities into active sprints (Sprint 0 through Sprint 6+), opens the slide-out Proof of Delivery (PoD) drawer, attaches verifiable SHA-256 telemetry digests, and advances the card to Testing / In Review. SMEs cannot self-certify work to Done.
  • Scrum Master / PM: Governs Work-in-Progress (WIP) column limits, monitors cycle time and throughput KPIs, and synchronizes activity roadmaps with project onboarding spreadsheets.
  • ISSO / ISSM Gatekeeper: Inspects the Testing queue. Regulatory sign-off requires that the program is onboarded, the activity is in an owned pillar, and each required ZTOM outcome has a verified passing SIEM hash. Without this proof, status changes return HTTP 422 and the card remains blocked.

4. Critical Path Engine & Integrated Master Schedule

Compliance tracking without an operational schedule results in unmanaged blockers. The application introduces a custom Splunk search command, | getcriticalpath (implemented in bin/get_critical_path.py), which executes a server-side Directed Acyclic Graph (DAG) Critical Path Method (CPM) using Kahn's topological sort.

The engine computes early and late start/finish dates alongside total float/slack for all milestone dependencies. The calendar logic dynamically calculates true operational time by skipping:

  • Weekend calendar intervals (Saturday/Sunday).
  • All 11 US statutory federal/DoD public holidays, including weekend observance shifts (e.g. Friday observance for Saturday holidays, Monday observance for Sunday holidays).
  • Project-wide team PTO exclusions defined in the pto_tok macro.

The resulting Gantt interface (zt_ims_gantt) provides real-time Schedule Performance Index (SPI) metrics and highlights critical-path milestone chains that risk slipping program Authority to Operate (ATO) deadlines.

5. Proof of Delivery (PoD) Vault & REST Endpoints

Compliance is proven by cryptographically bound evidence, not spreadsheet checkboxes. The Proof of Delivery (PoD) vault (zt_pod_handler.py) links each roadmap activity to:

  • Cryptographic SHA-256 digests of live Splunk CIM queries, raw event counts, or ACAS/VRAM vulnerability scans.
  • Multi-framework governance cross-mappings (DoD ZTA, NIST SP 800-53 Rev 5, SOC 2, and FedRAMP High).
  • Digital attestation metadata recording the authenticated Splunk session user and timestamp.
  • Internal audit logging to index=_internal sourcetype=zerotrust_audit.

6. Architecture Topology: AWS-DFD-Visualizer (Splunkbase #8628)

To bridge the gap between compliance schedules and live cloud infrastructure, companion project AWS-DFD-Visualizer (Splunkbase #8628, v2.8.7) renders cloud asset inventory onto NIST SP 800-207 Three-Plane swimlanes:

POLICY COMPONENTS IDENTIFIED IN TOPOLOGY

  • PEP (Policy Enforcement Point) & PIP (Policy Information Point): Workload sensors and posture checkers fed by ForeScout C2C, Trellix, Microsoft Defender for Endpoint (MDE), and Tenable.
  • PDP (Policy Decision Point), PE (Policy Engine), & PA (Policy Administrator): Orchestrated control logic anchored by enterprise SIEM policies and automated playbooks.
// CLAIMS_BOUNDARY: OBSERVATION VS. ENFORCEMENT

AWS-DFD-Visualizer detects CSP asset environments (AWS, Azure, GCP) and marks topology paths that miss an expected control, such as unapproved direct SSH (port 22) ingress. A marked path is an operational finding to review. It does not prove that a policy engine actively dropped or blocked unauthorized traffic, nor does diagram generation constitute an automated compliance certificate. A formal audit determination remains an independent regulatory review of cryptographic evidence.

7. System Boundaries & Operational Reality

In accordance with SuhLabs engineering principles, the capabilities and boundaries of the v1.1.7 pilot release are documented transparently:

Table 7.1: Documented system boundaries and technical limits in v1.1.7
Subsystem Implementation Reality in v1.1.7 Documented Boundary & Next Stage
Cross-Collection Sync Best-effort update-only sync from zt_agile_stories to compliance and IMS collections. Sync updates existing records. It is not a distributed two-phase atomic commit (2PC). If an update fails, an error is recorded to _internal.
ISSO / EDIPI Stage-Gate Workflow gating uses simulated DoD EDIPI digital signatures to enforce verification criteria. The server binds the SHA-256 of the acceptance. Hardware smartcard CAC mutual TLS authentication is queued for the post-pilot ATO milestone.
Predictive Risk Analytics Risk scoring and maturity tier evaluation run on native Splunk SPL eval over KV lookups. No external MLTK (Machine Learning Toolkit) app dependency is required. Scoring is deterministic rule logic, not black-box neural inference.
CPM Predecessors Server-side topological sort in | getcriticalpath operates on comma-separated milestone IDs. Predecessors formatted as semicolon-separated roadmap titles are ignored by CPM calculations until mapped to milestone IDs.
Discovery Telemetry Automated discovery scheduled searches populate observation state in the KV store. Telemetry volume does not automatically mark an activity Compliant. A single passing hash confirms outcome proof; continuous authorization (cATO) requires recurring verification.
