Rethinking Zero Trust: From Product Purchases to Logical Control Evidence

Published on Splunk Community: "Rethinking Zero Trust: From Product Purchases to Logical Control Evidence"

1. Buying a tool does not close a task

Zero Trust work stalls when a team treats it as a product to buy. A role owner sees a task on the roadmap and procures a tool to mark the task done. The DoD Zero Trust Execution Roadmap and NIST SP 800-207 describe outcomes. Meeting an outcome takes some mix of technical, logical, and administrative controls. A vendor feature list is not that mix.

Each course-of-action task has a phase, a target maturity, and a boundary: user, device, application, data, or network. The record for that task is which control is in place, what it observes, and which outcome it is supposed to meet. A SIEM, an EDR, or a network access-control product does not produce that record by itself.

2. Splunk App for Zero Trust Execution (9582)

The open-source Splunk App for Zero Trust Execution (Splunkbase 9582) loads a DoD course-of-action roadmap from an Excel file through the Splunk Lookup Editor. Navigation is the seven Zero Trust pillars: User, Device, Application/Workload, Data, Network, Automation, and Visibility. Each task is a tab. People working the task write status updates and attach log evidence in the app. The app assembles those entries into a Proof of Delivery for an ISSO or CISO to review and sign. A task with no evidence is listed as a milestone, so the same app is also the schedule.

Teams without a SIEM can track the same task list in Microsoft Planner. Each task's outcome definition can be stored as JSON, and Planner labels can mark Discovery, Phase 1, and Phase 2, plus predecessors and successors. Planner does not ingest logs and does not build the proof package. Someone copies evidence in by hand. In the Splunk app, log evidence is attached in the tool and the proof package is generated from the entries.

3. AWS-DFD-Visualizer (8628, v2.8.3)

AWS-DFD-Visualizer (Splunkbase 8628, v2.8.3) draws the current cloud inventory as a diagram. It groups assets into tiers (web, mid-tier, data stores, containers) and places them on the three NIST SP 800-207 planes: Identity, Policy and Control, and Infrastructure/Data. The layout follows that publication. The project targets DoD Impact Level 5 environments. The diagram shows where the policy components sit. It is a picture of inventory plus those labels. A compliance determination is a separate review of the evidence.

Policy components the diagram labels

  • PEP (Policy Enforcement Point) & PIP (Policy Information Point): Real-time posture checks fed by tools like ForeScout C2C, Trellix, Microsoft Defender for Endpoint (MDE), and Tenable.
  • PDP (Policy Decision Point), PE (Policy Engine), PA (Policy Administrator) & PAP (Policy Administration Point): Orchestrated control logic anchored by SOAR playbooks and enterprise SIEM policies (Splunk/Sentinel).

The app detects whether the inventory is AWS, Azure, or GCP and marks paths that miss an expected control, such as SSH on port 22 open to ingress. A marked path is a finding to check. It does not show that a policy engine blocked the traffic.

4. Demand signal

Further work on the Splunk App for Zero Trust Execution depends on whether people use the pieces already published. The signals are downloads and installs of AWS-DFD-Visualizer (Splunkbase 8628), comments on the Splunk Community post, and whether teams ask for the Splunk workflow or the Planner workflow.

5. The record

A SIEM, an EDR, or a network access-control product can supply the logs. The record that matters ties each course-of-action task to a control and to evidence. Splunk App 9582 builds that record from entries in the app. Planner can hold the same task list if someone files the evidence by hand.
