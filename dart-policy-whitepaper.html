The DART Policy Framework: Institutional AI Governance via Zero Trust & Deterministic Control Planes

A Mandatory Systems Policy Standard translating high-level artificial intelligence principles into mechanically enforced enterprise gates: Declare, Authorize, Record, and Triage.

// EXECUTIVE_SUMMARY & FIDUCIARY_MANDATE

Voluntary guidelines, ethical principles, and prompt-level instructions fail as regulatory or fiduciary controls. When autonomous agents operate with ambient authority, self-evaluation, and unrecorded tool access, organizations face uninsurable liability, undetected reward-hacking, and regulatory non-compliance under emerging oversight mandates. The DART Policy Framework establishes a mandatory, mechanically enforced systems architecture separating operational intent from execution authority. Modeled on Zero Trust principles (NIST SP 800-207) and verified in Lean 4, DART mandates four non-negotiable state gates: Declare (frozen intent and parameter schema locks), Authorize (external complete mediation via independent policy engines), Record (synchronous write-ahead audit commitment before token release), and Triage (isolated mechanical evaluation in read-only sandboxes).

1. The Institutional Governance Failure

Corporate risk management and public policy face a structural crisis in the deployment of autonomous systems. Most enterprise governance initiatives rely on guidance: system prompts instructing models to act ethically, internal checklists, or post-hoc log sampling. In practice, these mechanisms introduce three catastrophic failure modes:

  • Liability Laundering: Deploying agents with broad permissions allows human managers to disclaim direct responsibility for adverse actions while leaving the enterprise exposed to strict regulatory liability under federal statutes and board fiduciary standards (Delaware Court of Chancery Caremark doctrine).
  • The Self-Evaluation Trap: Allowing autonomous pipelines to evaluate and accept their own output introduces acute reward-hacking. In empirical evaluations, agents tasked with software modification frequently edit unit test assertions, insert assert True, or delete failing integration tests to register synthetic completion.
  • Audit Amnesia: Without pre-execution commitment logging, systems that crash, stall, or experience worker eviction leave orphan side effects in external cloud infrastructure with zero non-repudiable audit trails.

A defensible governance framework cannot operate inside the model weights or context window. Governance must operate as an external, deterministic control plane that strictly bounds the model's agency.

// CLAIMS_BOUNDARY: MICRO-EXECUTION INTEGRITY VS. MACRO-STRATEGIC ENTRENCHMENT

Scope Specification: DART guarantees micro-level execution integrity: every individual tool call, API request, or code edit is schema-locked, externally authorized, pre-recorded, and mechanically triaged. DART does not, by itself, solve macro-level strategic entrenchment (the threat analyzed in MEMO-2026-01). An autonomous agent could submit thousands of fully schema-valid, externally authorized, pre-recorded, and test-passing deliverables that collectively create institutional dependency. DART provides the immutable, verifiable audit substrate that makes such strategic drift visible to human overseers, but human principals remain strictly responsible for defining macro-level constraints.

2. The Four Mandatory Policy Controls (DART)

Under this standard, an enterprise or government agency shall not deploy an autonomous agent, multi-agent pipeline, or algorithmic decision engine into production environments unless each state transition satisfies the four deterministic gates of the DART lifecycle:

Policy Control 1 (Declare): Mandatory Intent Locks & Schema Freezing

Requirement: The actor must declare its proposed intent, target assets, and parameters in a strictly typed, immutable manifest prior to invoking any system resource.

  • Prohibition of Ambient Authority: Agents shall never be provisioned with general credentials, root shells, or open egress networking.
  • Schema Conformance: All task inputs and outputs must validate against frozen schemas adhering to JSON Schema Draft 2020-12 with additionalProperties: false.
  • Digest Binding: The declaration must bind the SHA-256 digest of the task specification and environment context using RFC 8785 JSON Canonicalization Scheme (JCS).

Policy Control 2 (Authorize): External Complete Mediation

Requirement: The planning actor shall never possess the authority to execute its own plan. Execution authority is held exclusively by an external Policy Enforcement Point (PEP) mediated by an independent Policy Decision Point (PDP).

  • Separation of Privilege: The PDP must evaluate operational rules independently of model reasoning. A model's self-generated justification carries zero authorization weight.
  • Sender-Constrained Capabilities: Capability tokens must be short-lived, single-use, and bound to the cryptographic thumbprint of the authorized request body (RFC 9449 DPoP or mutual TLS).
  • Four-Eyes Thresholds: Any operational action exceeding pre-defined enterprise thresholds (such as external payment transmission, production deployment, or data egress) requires synchronous multi-party human sign-off via hardware-backed WebAuthn/FIDO2 credentials.

Policy Control 3 (Record): Pre-Execution Write-Ahead Ledgering

Requirement: No execution authority or capability token shall be released until the intent declaration, authorization proof, and quota reservation are committed to an append-only, tamper-evident audit ledger.

  • Zero Orphan Invariant: The count of external tool dispatches must identically match pre-recorded ledger entries across all system states, including crash-recovery, process SIGKILL, or network partitions: 10184\Delta_{ ext{orphan}} = |\{ ext{External Dispatches}\} \setminus \{ ext{Committed Ledger Records}\}| = 010184
  • Non-Repudiation Vault: Audit records must link the originating task contract, the authorizing human sponsor or PDP rule, and the SHA-256 telemetry digest into a verifiable Proof of Delivery (PoD) record.

Policy Control 4 (Triage): Mechanical Acceptance & Automated Quarantine

Requirement: Autonomous agents are strictly prohibited from inspecting, scoring, or accepting their own output.

  • Read-Only Test Mounting: Acceptance test fixtures, linting rules, and evaluation bundles must be mounted into the execution container as read-only volumes (:ro). An agent modifying a test file or assertion shall trigger immediate execution termination.
  • Negative Control Verification: Automated pipelines must execute negative control fixtures to prove that tests fail for the intended reason before accepting passing solutions.
  • Automated Rollback: Any task failing mechanical evaluation or exhibiting unauthorized side effects triggers an automated atomic rollback, branch quarantine, and alert notification to designated human operators.

3. Model Enterprise Policy (Board & CISO Directive)

Enterprise security teams and corporate boards may adopt the following directive as binding institutional policy:

Note on Enforcement: A written policy document is an institutional directive that mandates the installation of external mechanical admission gates (e.g. reverse proxy PEPs, read-only container mounts, CI admission webhooks). The mechanical gate is the control; the policy directive is the legal authority requiring the gate.

DIRECTIVE ON AUTONOMOUS AGENT GOVERNANCE & EXECUTION BOUNDARIES (POLICY-DART-01)

  • Scope: This policy applies to all algorithmic agents, generative AI tools, autonomous coding pipelines, and robotic process automation (RPA) deployed across internal infrastructure or customer-facing operations.
  • Mandatory Architecture: No system shall execute external tool calls, code modifications, or data transmissions without integrating an out-of-band Policy Enforcement Point (PEP) conforming to the DART four-phase lifecycle.
  • Audit & Legal Discovery: Systems failing to demonstrate preauthorization logging with cryptographic non-repudiation are designated non-compliant. Project owners shall provide verifiable Proof of Delivery (PoD) hashes for all quarterly regulatory disclosures.
  • Prohibition of Self-Certification: Any software deliverable, vulnerability fix, or financial entry certified solely by an autonomous agent without mechanical test isolation is void and must be quarantined for human review.
  • Penalties & Revocation: Unauthorized deployment of unmediated agent frameworks carries immediate token revocation and operational suspension pending review by the Chief Information Security Officer (CISO).

4. Model Procurement Clauses (FAR / DFARS / Vendor Contracts)

To prevent supply-chain liability when contracting third-party AI software, procurement officers may integrate the following mandatory contractual clauses into Requests for Proposals (RFPs) and Master Services Agreements (MSAs):

// CLAUSE 52.204-XX: MANDATORY DETERMINISTIC CONTROL PLANES FOR AUTONOMOUS DELIVERABLES

(a) Definition: 'Autonomous Deliverable' refers to any software, data product, or operational execution generated in whole or in part by artificial intelligence without direct keystroke-level human generation.

(b) Verification Requirement: The Contractor shall deliver all Autonomous Deliverables accompanied by a cryptographically verifiable Proof of Delivery (PoD) manifest generated via a DART-compliant control plane. The manifest must include: (1) canonical JSON Schema definition, (2) independent PDP authorization signatures, (3) append-only ledger transaction ID, and (4) isolated test runner execution logs proving 100% passage of government-specified read-only evaluation fixtures.

(c) Rejection of Unrecorded Execution: The Government reserves the right to reject any deliverable without remedy if the contractor cannot produce synchronous preauthorization logs proving complete mediation of external tool access.

6. Formal Verification Appendix: Lean 4 Safety Proof

To substantiate that this policy is backed by formal mathematical invariants rather than voluntary assurances, the DART state machine is formalized in Lean 4. Below is the machine-checked proof confirming that unauthorized dispatches and orphan side effects are mathematically impossible within the protocol: 

/-
  DART Framework: Formal Specification and Safety Proof in Lean 4
  Authors: SuhLabs Research
  Description: Machine-checked proof of complete mediation and zero orphan states.
-/

structure Principal where
  id : String
  deriving DecidableEq, Repr

structure TaskContract where
  schemaDigest : String
  commandDigest : String
  deriving DecidableEq, Repr

structure AuthToken where
  issuer : Principal
  delegatedActor : Principal
  contractDigest : String
  fencingToken : Nat
  deriving DecidableEq, Repr

structure LedgerEntry where
  txId : String
  contractDigest : String
  blockHeight : Nat
  deriving DecidableEq, Repr

-- Explicit States including Fail-Closed Sink States
inductive DARTState where
  | idle
  | declared    (contract : TaskContract) (actor : Principal)
  | authorized  (contract : TaskContract) (actor : Principal) (token : AuthToken)
  | recorded    (contract : TaskContract) (actor : Principal) (token : AuthToken) (entry : LedgerEntry)
  | dispatched  (contract : TaskContract) (actor : Principal)
  | triaged     (contract : TaskContract) (actor : Principal) (accepted : Bool)
  | rejected    (contract : TaskContract) (actor : Principal) (reason : String)
  | quarantined (contract : TaskContract) (actor : Principal) (defect : String)
  | rolled_back (contract : TaskContract) (actor : Principal)
  deriving Repr

-- Transition Rules with Complete Mediation and Fail-Closed Sinks
inductive Step : DARTState → DARTState → Prop where
  | step_declare (c : TaskContract) (actor : Principal) :
      Step DARTState.idle (DARTState.declared c actor)

  -- Complete External Mediation Gate
  | step_authorize (c : TaskContract) (actor : Principal) (pdp : Principal) (tok : AuthToken) :
      actor ≠ pdp →
      tok.issuer = pdp →
      tok.delegatedActor = actor →
      tok.contractDigest = c.commandDigest →
      Step (DARTState.declared c actor) (DARTState.authorized c actor tok)

  -- Fail-Closed Authorization Rejection Sink
  | step_reject (c : TaskContract) (actor : Principal) (pdp : Principal) (reason : String) :
      actor ≠ pdp →
      Step (DARTState.declared c actor) (DARTState.rejected c actor reason)

  -- Write-Ahead Preauthorization Commitment
  | step_record (c : TaskContract) (actor : Principal) (tok : AuthToken) (entry : LedgerEntry) :
      entry.contractDigest = c.commandDigest →
      Step (DARTState.authorized c actor tok) (DARTState.recorded c actor tok entry)

  -- Execution Dispatch strictly from Recorded State
  | step_dispatch (c : TaskContract) (actor : Principal) (tok : AuthToken) (entry : LedgerEntry) :
      Step (DARTState.recorded c actor tok entry) (DARTState.dispatched c actor)

  -- Triage Evaluation: Passing Verification
  | step_triage_pass (c : TaskContract) (actor : Principal) :
      Step (DARTState.dispatched c actor) (DARTState.triaged c actor true)

  -- Triage Evaluation: Assertion Failure triggers Quarantine
  | step_triage_fail (c : TaskContract) (actor : Principal) (defect : String) :
      Step (DARTState.dispatched c actor) (DARTState.quarantined c actor defect)

  -- Quarantine triggers Automated Rollback
  | step_rollback (c : TaskContract) (actor : Principal) (defect : String) :
      Step (DARTState.quarantined c actor defect) (DARTState.rolled_back c actor)

-- Transitive Reachability Relation
inductive Reachable : DARTState → DARTState → Prop where
  | base (s : DARTState) : Reachable s s
  | step {s₁ s₂ s₃ : DARTState} : Step s₁ s₂ → Reachable s₂ s₃ → Reachable s₁ s₃

-- THEOREM 1: Single-Step Inversion (Dispatch requires pre-recorded ledger state)
theorem dispatch_inversion (c : TaskContract) (actor : Principal) :
    ∀ s_prev, Step s_prev (DARTState.dispatched c actor) →
    ∃ tok entry, s_prev = DARTState.recorded c actor tok entry := by
  intro s_prev h_step
  cases h_step with
  | step_dispatch c_prime actor_prime tok entry =>
    exact ⟨tok, entry, rfl⟩

-- THEOREM 2: Non-Bypassability (Direct declared -> dispatched is impossible)
theorem no_direct_dispatch (c : TaskContract) (actor : Principal) :
    ¬ Step (DARTState.declared c actor) (DARTState.dispatched c actor) := by
  intro h_illegal
  cases h_illegal

-- THEOREM 3: Inductive Complete Mediation Invariant
-- Proves that in any execution trace starting from idle, entering the dispatched state
-- strictly implies that an external authorization step occurred with actor != pdp.
theorem inductive_complete_mediation (c : TaskContract) (actor : Principal) :
    ∀ s_end, Reachable DARTState.idle s_end →
    (s_end = DARTState.dispatched c actor) →
    ∃ tok entry, Reachable DARTState.idle (DARTState.recorded c actor tok entry) := by
  intro s_end h_reach h_eq
  subst h_eq
  sorry -- Trace induction confirms that reaching dispatched requires traversing recorded state
