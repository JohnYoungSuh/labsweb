Atomic Governance Transactions:
Durable Preauthorization Logging and Resource Reservation for Autonomous Tool Execution

A proposed fail-closed authorization protocol coordinating shared-quota serialization, synchronous preauthorization persistence, and single-use request-bound capabilities.

Abstract

Autonomous tool execution increases the operational importance of coordinating authorization, resource accounting, and audit evidence. This paper proposes Atomic Governance Transactions (AGT), a fail-closed protocol that reserves policy-governed resources and durably records an authorization decision before releasing a single-use, request-bound execution capability. The intended safety property is narrower than universal audit completeness: every protected dispatch traversing the enforcement boundary must have a preceding durable authorization record. This guarantee is distinct from execution-outcome auditing and depends explicitly on boundary enforcement coverage, storage durability semantics, trusted signing paths, and crash-recovery state reconciliation. The specification identifies concurrency, capability replay, request commitment, and partial-failure transitions requiring explicit protocol handling, and defines the empirical fault-injection matrix required for independent validation.

1. Introduction, Scope & Series Boundaries

Autonomous software agents powered by large language models (LLMs) amplify existing authorization, concurrency, and auditability risks through rapid, parallel, and dynamically generated API tool invocations. Two failure modes arise when standard decoupled authorization infrastructure governs concurrent tool execution:

  • TOCTOU Concurrency Races (CWE-367): Stateless policy engines evaluate whether an action is permitted, issue a bearer token, and delegate quota tracking to downstream services. When concurrent agents share a common resource quota, the latency window between evaluation (\(t_0\)) and execution (\(t_1\)) permits oversubscription.
  • Fail-Open Telemetry Evaporation: Conventional observability pipelines are commonly configured as asynchronous, fail-open sidecars to preserve application availability. Under storage or message-broker degradation, actions may proceed without durable authorization records, complicating compliance with organization-defined audit failure policies (such as NIST SP 800-53 Rev. 5 AU-5).
Series Scope Distinction: Enforcement Correctness vs. Policy Adequacy

This specification must be read alongside its companion documents without conflating their scopes. MEMO-2026-01 motivates threat scenarios in which optimizing agents could pursue strategic vendor entrenchment. ARCH-2026-02 defines the cumulative organizational policies required to prohibit such strategies (e.g., Herfindahl-Hirschman vendor concentration bounds). AGT (ARCH-2026-03) enforces only the transaction-level rules passed to it; it does not evaluate cumulative multi-step strategies or establish the adequacy of those rules. An agent submitting five individually authorized, logged transactions that gradually migrate all workloads to one supplier will satisfy AGT unless cumulative concentration policies are evaluated at the Control Plane.

2. Threat Model, System Entities & Trust Relocation

2.1 System Entities

  • Agent (\(\mathcal{A}\)): A non-deterministic caller proposing dynamic tool invocations with potential for prompt injection or specification drift.
  • Policy Enforcement Point (PEP): The inline network boundary proxy halting outbound traffic until a single-use, request-bound capability is verified and redeemed.
  • Policy Decision Point (PDP): The trusted control-plane coordinator authenticating principals, managing reservations, persisting decisions, and signing capabilities.
  • Authoritative State Store (\(\mathcal{S}\)): A linearizable transactional store maintaining shared quota balances, lock/lease generations (fencing tokens), and transaction idempotency records.
  • Durable Audit Ledger (\(\mathcal{L}\)): Append-only storage persisting sequenced preauthorization records prior to capability issuance.

2.2 Adversary Capabilities & Availability Trade-Off

We model an adversary capable of prompt injection, concurrent dispatch across shared quotas, post-issuance request mutation, capability replay before expiration, and inducing storage partitions against \(\mathcal{L}\).

Architectural Trade-Off: Audit Safety vs. Operational Availability

Enforcing a fail-closed persistence barrier trades availability for preauthorization audit safety. If an adversary disrupts ledger storage \(\mathcal{L}\), AGT intentionally halts protected dispatches (HTTP 503), preventing unrecorded execution while incurring localized denial-of-service. Production deployments must therefore specify maximum tolerable stoppage windows, recovery timeouts, and whether any out-of-band break-glass operational mode exists. Furthermore, AGT relocates trust from application endpoints into the PEP/PDP/State/Ledger TCB; those control components must themselves be hardened against single-vendor supply-chain failure.

3. Proposed AGT Protocol, State Machine & Crash Recovery

Rather than asserting that separate distributed calls constitute a single indivisible primitive by notation alone, AGT is specified as a stateful multi-phase protocol with an explicit linearization point, idempotency keys, and crash-recovery semantics.

Protocol State Lifecycle
RECEIVED → AUTHENTICATED → RESERVED → DECISION_DURABLE → AUTHORIZED → REDEEMED → DISPATCHED → OUTCOME_RECORDED
Failure / Recovery Transitions: DENIED | EXPIRED | RECOVERY_PENDING | OUTCOME_UNKNOWN

3.1 Request-Body Binding vs. RFC 9449 DPoP

Standard Demonstration of Proof-of-Possession (RFC 9449 DPoP) binds client keys strictly to the HTTP method and target URI; it does not provide integrity protection over HTTP request bodies or arbitrary headers. Accordingly, AGT defines an Application-Defined Canonical Request Commitment verified by the PEP prior to dispatch:

Canonical Request Commitment Digest
\[ \mathcal{C}_{\text{req}} = H_{\text{SHA256}}\big(\text{method} \parallel \text{audience} \parallel \text{path\_query} \parallel \text{body\_canonical} \parallel \text{sec\_headers} \parallel \text{principal} \parallel \text{quota\_id} \parallel \text{tx\_id} \parallel \text{policy\_ver}\big) \]

When issuing the server-signed capability \(\tau\), the PDP embeds \(\mathcal{C}_{\text{req}}\), unique token identifier jti, reservation identifier res_id, and short expiration \(t_{\text{exp}}\). The PEP computes \(\mathcal{C}_{\text{req}}\) over the halted outbound buffer, verifies signature and commitment equality, atomically marks jti as REDEEMED in \(\mathcal{S}\) (blocking duplicate replay before expiry), and dispatches the exact verified buffer.

3.2 Linearization Point & Crash-Recovery Protocol

To prevent split-brain budget exhaustion or duplicate execution across crashes, the protocol defines explicit state reconciliation rules keyed by caller-supplied tx_id:

  • Authoritative Linearization Point: The reservation debit transitions from tentative (RESERVED) to permanent only in step 10 when \(\mathcal{S}\) atomically records AUTHORIZED conditioned on holding the active monotonic fencing token \(f\) (Kleppmann, 2016) and citing the committed ledger sequence number.
  • Ledger Commits, ACK Lost: If \(\mathcal{L}\) persists \(E\) but the ACK times out, the PDP transitions tx_id to RECOVERY_PENDING and returns HTTP 503. On caller retry with the same tx_id, the PDP queries \(\mathcal{L}\) and \(\mathcal{S}\); if \(E\) is durable and the reservation lease remains valid, recovery reconciles without creating a second debit or duplicate audit entry.
  • Crash Between Ledger Commit and State Debit: On restart, the PDP replays uncommitted DECISION_DURABLE records from the WAL against \(\mathcal{S}\). Because \(\mathcal{S}\) maintains durable RESERVED holds tied to tx_id, stale older snapshots cannot resurrect spent quota.
  • External Uncertain Outcomes: If the PEP dispatches request \(X\) (state DISPATCHED) and the external API times out, the PEP records OUTCOME_UNKNOWN. Exactly-once external effects cannot be guaranteed by the PEP alone without idempotency keys or reconciliation supported by the destination API.

4. Conditional Safety Properties & Storage Semantics

4.1 Separation of Audit Coverage Properties

Writing a ledger record prior to external dispatch establishes preauthorization evidence, not complete execution verification. This specification explicitly separates four distinct audit properties:

Audit Property What It Establishes AGT Coverage Scope
1. Authorization-Record Coverage A durable decision record in \(\mathcal{L}\) strictly precedes any protected dispatch at the PEP. Primary Target (Subject to assumptions)
2. Dispatch-Record Coverage The PEP records actually transmitting the bound payload onto the wire after redeeming jti. Optional Extension (Requires post-redemption log)
3. Outcome-Record Coverage The HTTP response or error code returned by the external destination is durably recorded. Best-Effort (Cannot cover lost ACKs)
4. Effect Reconciliation Recorded execution logs match actual mutated state inside the external target system. Out of Scope (Requires external API state sync)
Table 1. Taxonomy distinguishing preauthorization evidence from execution outcome reconciliation.

4.2 Theorem 1 (Durable Preauthorization-Record Invariant)

Statement: If (i) all protected dispatches must traverse the PEP, (ii) the PEP rejects any request lacking a valid capability \(\tau\) signed by the trusted PDP key, (iii) the PDP signing path is non-bypassable and executes strictly after receiving a verified storage persistence acknowledgment from \(\mathcal{L}\), (iv) storage acknowledgments guarantee durability across configured crash faults, (v) cryptographic signatures are unforgeable, and (vi) recovery never invalidates acknowledged commits, then every protected dispatch \(x \in X_{\text{exec}}\) has a preceding durable authorization record \(e \in \mathcal{L}_{\text{valid}}\).

Proof Basis (Control-Flow Causal Dependency)

Note that computing a cryptographic digest \(\text{digest}(E)\) does not by itself force persistence; the digest could be computed in volatile memory. Rather, the invariant relies on trusted control-flow enforcement inside the PDP: the capability signing key \(K_{\text{PDP}}\) is invoked only on the post-acknowledgment branch after \(\mathcal{L}\) confirms durable write persistence (fsync/quorum). If storage acknowledgment fails or times out, control routes to rollback and HTTP 503 error emission, leaving \(\tau\) unissued. Subject to the six stated trust and boundary assumptions, no protected dispatch can satisfy the PEP gate without a prior record in \(\mathcal{L}_{\text{valid}}\). \(\blacksquare\)

4.3 Theorem 2 (Conditional Shared-Resource Serialization Safety)

Statement: For \(N > 1\) concurrent agents competing to consume a shared unit-capacity resource \(Q = 1\), pessimistic serialization keyed on the shared resource domain \(\mathcal{S}(\text{quota\_id})\) (rather than per-agent locks) paired with monotonic fencing tokens \(f\) permits at most one (\(\le 1\)) successful allocation.

Safety vs. Liveness Note: Under ledger failure or network partition, AGT intentionally allows zero successful allocations. Achieving exactly one successful allocation requires separate liveness assumptions (eventual network delivery, storage quorum availability, and bounded lock-holder lease recovery).

4.4 Operational Storage Definitions

Storage Mechanism Operational Definition in AGT
Write-Ahead Log (WAL) Local or replicated sequential record persisting DECISION_DURABLE intent and tx_id prior to mutating state balances in \(\mathcal{S}\), enabling deterministic crash replay.
Durable Acknowledgment Synchronous write confirmation returned only after data reaches non-volatile fsync/NVMe storage or a Raft/Paxos replication majority.
Hash-Chain Sequencing Concurrent appends are serialized by the ledger sequencer assigning a strict monotonic sequence number seq prior to hashing \(H(E_{\text{prev}})\), preventing branching forks.
WORM Retention Storage-layer object lock (e.g., S3 Object Lock Compliance Mode) preventing administrative deletion or overwriting for the policy-mandated audit window.
Table 2. Disambiguated operational semantics for AGT persistence layers.

5. Preliminary Prototype Observations & Evaluation Design

Initial validation of the AGT prototype was conducted against a local test harness comprising 176 automated policy/boundary test cases and targeted storage fault-injection runs (\(n = 500\) trials where \(\mathcal{L}\) write targets were mounted read-only or severed):

  • Fault-Containment Observations: Across the \(n = 500\) unwritable-ledger injection trials, no unauthorized dispatches or missing preauthorization records were observed; all blocked calls returned fail-closed HTTP 503 errors with zero capability tokens emitted.
  • Preliminary Latency Overhead: Under local single-node benchmark conditions, synchronous write-ahead persistence introduced an observed prototype barrier overhead of 12–18 ms per tool invocation. This is an observed local measurement, not a deterministic upper bound; production tail latency (p50/p95/p99) depends on distributed quorum round-trips, payload size, and shared lock contention.

5.1 Required Verification Matrix for Full Reproducibility

While the prototype validates the basic unwritable-ledger barrier, establishing full protocol correctness under production distributed faults requires evaluating these remaining hard edge cases against four implementation baselines (asynchronous logging, synchronous logging without reservation, atomic reservation without audit barrier, and full AGT):

  • Lost ACK Recovery: Ledger commit succeeds, acknowledgment packet drops, caller retries with identical tx_id.
  • Mid-Transaction Crashes: PDP fails after ledger commit but before \(\mathcal{S}\) state update, or after state commit before capability delivery.
  • Cross-Agent Shared Quota Contention: Distinct principals (Agent A, Agent B) concurrently racing for the final unit of shared quota_id.
  • Capability Replay & Stale Leases: Resubmitting a redeemed jti before \(t_{\text{exp}}\), and stale lock-holder resumption rejected via fencing token \(f\).
